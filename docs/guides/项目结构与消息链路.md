# 项目结构与消息链路

本文按 2026-10-31 的实际源码说明当前部署，旧文档中的工作区目录、SnowLuma 运行方式和旧预设行为不应直接套用。

## 前端与后端

- 前端为 `public/dashboard.html`、`dashboard.css`、`dashboard.js`，使用原生 HTML/CSS/JavaScript；五页工作台展示状态、会话、记忆、Token、活动，预算表单可保存自动聊天限制。详细配置控制台为 `public/console.html`，音色设置为 `public/speech-setup.html`。
- 业务后端为 Node.js ES Modules，入口 `src/bridge.js`，使用原生 HTTP 服务。网页与接口共用这个进程，前后端位于同一个仓库；Nginx 提供 HTTPS，只代理指定工作台路径。
- DSH 是独立的智能体引擎，负责模型调用、上下文和工具回合；NapCat 是独立的 QQ 网关，以 OneBot 协议连接后端。服务部署在云服务器，电脑上的网页和源码不需要一直运行。

## 消息链路

```text
QQ 消息 → NapCat → OneBot WebSocket → bridge.js
                                    ↓ 准入、身份、引用、唤醒与预算检查
                                  DSH → DeepSeek API
                                    ↓ 工具或回合事件
                     bridge.js → 发送前复核 → NapCat → QQ

浏览器 → HTTPS/Nginx → bridge.js 统一认证 → 工作台/管理接口
```

语音由桥接调用独立语音适配，当前云端合成使用硅基流动；切换聊天 API 不等于切换语音服务。

## 本轮管理接口拆分

`createManagementRoutes(...)` 创建一个长期存在的处理器，承接：

- `GET/POST /api/whitelist`
- `GET /api/dsh/model`
- `POST /api/dsh/effort`

主入口先完成 Host、密码、智能体隔离和 CSRF 检查，然后委派给处理器。处理器只接收必要的配置读写、会话权限协调、模型代号更新和目录查询能力，不直接接触 QQ 网关。未匹配的路径/方法继续原路由，接口 URL、响应结构与前端调用保持一致。

配置先原子落盘，成功后才更新内存与协调会话；磁盘失败不能提前应用设置。改推理档位不会新建回合，已有会话下一次使用时才重新选模。模型目录并发读取合并与失败日志去重属于处理器实例，不使用跨实例全局 Promise。

重构主要降低维护和测试成本，不代表模型生成速度或 Token 使用量已经降低。消息调度、未读水位和发送队列仍由主程序协调，后续应在现有回归约束下逐块拆分。

## 验证

```powershell
node --test scripts/test-management-module.mjs scripts/test-management-routes.mjs
```

测试使用临时配置、模拟 DSH 和本地 HTTP 服务；不读取生产凭据、不调用付费模型、不向 QQ 发送消息。源码重构应同时回归鉴权、权限撤销、模型热更新与已有消息流程，不能只验证语法。
